# llm-aviasales-parser

CLI для поиска лучших авиаперелётов на aviasales.ru. Python-проект живёт в корне
этого репозитория; манифесты **плагина** — в `.claude-plugin/`
(`plugin.json` + `marketplace.json`), скилл — в
`skills/aviasales-flight-search/SKILL.md` (обёртка над этим же CLI, без
дублирования кода).

Инструмент бьёт напрямую в реальный внутренний API aviasales.ru (v3.2,
двух-хостовый флоу `start` → `results`): вся поездка (все направления вместе,
включая мультигород) ищется ОДНИМ поиском. Авторизация берётся из cURL,
скопированного из браузера пользователя, — тело же запроса CLI строит сам
(cURL нужен только ради куки/заголовков, см. «Обновление cURL» ниже).

## Установка

### Требования: только `uv`
Единственная внешняя зависимость — [uv](https://docs.astral.sh/uv/): он сам
скачает нужный Python (3.14, см. `.python-version`) и поставит зависимости
проекта при первом `uv run`/`uv sync`. Отдельно устанавливать Python не нужно.

Проверить и при необходимости установить:
```bash
uv --version || curl -LsSf https://astral.sh/uv/install.sh | sh   # macOS/Linux
# Windows (PowerShell):
# powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

Скилл при запуске сам проверяет наличие `uv` и предлагает установить его этой
же командой, если он отсутствует.

### Как плагин Claude Code
В сессии Claude Code:
```
/plugin marketplace add sanederchik/llm-aviasales-parser
/plugin install aviasales-flight-search@aviasales-flight-search
```
(первая команда подключает маркетплейс из этого репозитория, вторая ставит
плагин из него; маркетплейс можно добавить и из терминала:
`claude plugin marketplace add sanederchik/llm-aviasales-parser`).

После установки скилл активируется автоматически, когда вы просите найти
билеты («найди билеты Москва → Бали в сентябре…»). Python-окружение при первом
запуске создаст `uv` — ничего собирать вручную не нужно.

### Как скилл Codex
Codex ищет скиллы в `~/.agents/skills` (и в `.agents/skills` внутри
репозитория). Скилл вызывает Python-CLI из корня этого репозитория, поэтому
клонировать нужно репозиторий целиком, а в папку скиллов положить симлинк
(копировать одну папку скилла нельзя — CLI останется за бортом):
```bash
git clone https://github.com/sanederchik/llm-aviasales-parser.git ~/.local/share/llm-aviasales-parser
mkdir -p ~/.agents/skills
ln -s ~/.local/share/llm-aviasales-parser/skills/aviasales-flight-search ~/.agents/skills/aviasales-flight-search
```
Перезапустите Codex — скилл подхватится автоматически (список: команда
`/skills`, явный вызов: `$aviasales-flight-search`).

### Вручную (разработка)
Из корня репозитория: `uv sync`. Для живых запросов также: `uv sync --extra live`
(ставит `curl_cffi` для TLS-имперсонации браузера — нужен только боевому
транспорту, офлайн-тестам не требуется).

## Схема конфига (`trip.json`)

```json
{
  "currency": "rub",
  "market_code": "ru",
  "trip_class": "Y",
  "passengers": {"adults": 2, "children": 0, "infants": 0},
  "directions": [
    {"from": "MOW", "to": "DPS",
     "date_window": {"earliest": "2026-09-01", "latest": "2026-09-30"},
     "stay_days": {"min": 30, "max": 50},
     "from_airports": ["DME", "SVO"], "to_airports": ["DPS"],
     "constraints": {"max_transfers": 1, "baggage": {"required": true, "min_weight_kg": 20},
                     "depart_time_of_day": ["morning", "afternoon"]}},
    {"from": "DPS", "to": "MOW",
     "date_window": {"earliest": "2026-12-01", "latest": "2026-12-31"}}
  ],
  "global_constraints": {
    "max_transfers": 1,
    "baggage": {"required": true, "min_weight_kg": 20, "large_handbag": true},
    "max_duration_minutes": 1440,
    "max_transfer_minutes": 300,
    "exclude_gulf_transfers": true,
    "max_price": 250000,
    "refundable_only": true,
    "depart_time": {"from": "06:00", "to": "12:00"}
  },
  "max_trip_days": 55,
  "same_airport_cities": ["MOW"],
  "search_budget": {"max_requests": 100, "date_samples_per_direction": 10,
                    "request_delay_seconds": {"min": 0.5, "max": 1.0}},
  "cache": {"ttl_minutes": 5}
}
```

Поля верхнего уровня:
- `directions` (обязательно, непустой список) — вся поездка целиком: и
  туда-обратно, и мультигород — это несколько записей в одном списке, все
  ищутся ОДНИМ запросом к API, а не отдельными one-way поисками. Каждая
  запись: `from`, `to` (IATA-коды городов/аэропортов) и обязательное
  `date_window: {earliest, latest}` (`YYYY-MM-DD`). Опционально `constraints`
  — переопределяет `global_constraints` для этого направления (любое
  не-`null` поле в `constraints` направления выигрывает у одноимённого в
  `global_constraints`, остальные наследуются оттуда). Опционально `stay_days: {min, max}` — пребывание в пункте назначения ЭТОГО
  направления: дата вылета СЛЕДУЮЩЕГО направления должна попасть в
  `[дата_вылета + min, дата_вылета + max]` (обе границы включительно; хотя бы
  одно из `min`/`max` обязательно). Считается по датам вылета — погрешность
  ±1 день от времени прилёта; комбинации дат вне диапазона не пробуются
  вовсе (экономят сетевой бюджет). На последнем направлении `stay_days`
  запрещён — после него нет следующего вылета. Опционально `from_airports` /
  `to_airports` — белый список IATA-кодов конкретных аэропортов вылета/
  прилёта этого направления (когда `from`/`to` — код города с несколькими
  аэропортами).
- `global_constraints` — жёсткие фильтры по умолчанию для всех направлений
  (пожелания не оптимизируются — оптимизируется только цена, см. ниже).
  Фильтры уходят на сервер в `filters_state` каждого `results`-запроса
  (`api_filters.py`; заодно всегда шлётся `sort: price_asc`) — сервер сужает
  выдачу до топ-200 подходящих билетов; клиентская проверка (`filters.py`)
  затем перепроверяет уже полученные билеты как страховку. Часть полей (см.
  список «только сервер» ниже) в ответе `results` нечем перепроверить и
  полагается целиком на серверную фильтрацию:
  - `max_transfers` — макс. число пересадок на направление;
  - `max_transfer_minutes` — макс. пауза между стыковочными рейсами;
  - `baggage` — объект `{"required": bool, "min_weight_kg": int,
    "large_handbag": bool}`: `required` — багаж обязателен на ВСЁМ билете
    (тариф общий, не на отдельное направление); `min_weight_kg` — мин. вес
    багажа в кг (на сервер уходит ближайший вниз порог 30/20/10,
    подразумевает `required: true`); `large_handbag` — большая ручная кладь
    (только серверная проверка — поле веса ручной клади парсер билетов не
    извлекает). Легаси `baggage_required: true` — синоним `baggage.required`;
  - `max_price` — макс. итоговая цена билета в валюте поиска;
  - `max_duration_minutes` — макс. длительность направления «от вылета до
    прилёта»;
  - `depart_time_of_day` / `arrive_time_of_day` — список значений
    `morning|afternoon|evening|night`; `depart_time_of_day` проверяется
    только для вылета ПЕРВОГО направления, `arrive_time_of_day` — только для
    прилёта ПОСЛЕДНЕГО;
  - `depart_time` / `arrive_time` — точный диапазон `{"from": "HH:MM", "to":
    "HH:MM"}` (границы включительно), в отличие от `*_time_of_day`
    применяется на своём направлении всегда, включая промежуточные;
  - `exclude_gulf_transfers: true` — исключить билеты с пересадкой через
    аэропорты Персидского залива
    (`DXB,DWC,AUH,SHJ,RKT,DOH,BAH,KWI,RUH,JED,DMM,MCT`);
  - `exclude_transfer_airports` — явный список IATA-кодов аэропортов
    пересадок для исключения (если задан, имеет приоритет над
    `exclude_gulf_transfers`);
  - `airlines` — белый список IATA-кодов авиакомпаний: каждый рейс
    направления (включая стыковочные сегменты) должен выполняться
    перевозчиком из списка;
  - `alliances` — список id авиационных альянсов (только сервер);
  - `agents` — список продавцов вида `"name|id"` (проверяется по числовой
    части id против `agent_id` выбранного предложения);
  - `payment_methods` — список способов оплаты, например `card`/`sbp` (только
    сервер);
  - `aircraft_models` — список кодов моделей ВС (только сервер);
  - `lowcosts` — включить/исключить лоукостеров (только сервер, `bool`);
  - `no_airport_change` — без смены аэропорта на пересадке (проверяется и
    клиентски: аэропорт прилёта пред. плеча = аэропорт вылета след.);
  - `no_night_transfers` — без ночных пересадок (только сервер);
  - `no_complex_transfers` — без «сложных» пересадок, UI-термин Aviasales
    (только сервер);
  - `no_recheckin_transfers` — без пересадок с повторной регистрацией (только
    сервер);
  - `no_interlines` — без интерлайнов (только сервер);
  - `convenient_transfers` — только «удобные пересадки» (только сервер);
  - `changeable_only` / `refundable_only` — только тарифы с возможностью
    обмена/возврата (проверяется по `additional_tariff_info` предложения;
    `None`, т.е. данные неизвестны, трактуется как «не подходит»).
- `max_trip_days` (опционально) — макс. число дней между датой вылета ПЕРВОГО
  направления и датой вылета ПОСЛЕДНЕГО (длительность всей поездки);
  комбинации дат с большим интервалом не пробуются вовсе.
- `same_airport_cities` (опционально, верхний уровень) — список кодов
  городов, для которых требуется вылет и возврат из ОДНОГО аэропорта города
  (актуально для городов с несколькими аэропортами); только серверный
  фильтр.
- `passengers` — `adults`/`children`/`infants` (по умолчанию 1/0/0).
- `trip_class` (по умолчанию `Y`), `currency` (по умолчанию `rub`),
  `market_code` (по умолчанию `ru`).
- `search_budget.max_requests` (по умолчанию `100`) — жёсткий потолок РЕАЛЬНЫХ
  сетевых поисков ТОЛЬКО Фазы 2 (верификация комбо; кэш-хиты в лимит не входят).
  Фаза 1 (поплечевой свип) им не ограничена — она всегда перебирает все даты
  окон. `date_samples_per_direction` — легаси-поле, на двухфазный алгоритм не
  влияет. `request_delay_seconds` (по умолчанию `{"min": 0.5, "max": 1.0}`) —
  диапазон «человеческой» паузы в секундах перед каждым HTTP-вызовом (один поиск
  = start + несколько поллингов, т.е. несколько пауз); повышайте при риске
  бот-блокировки, понижайте ради скорости.
- `cache.ttl_minutes` (по умолчанию `5`) — сколько минут переиспользовать
  сырой зонд без похода в сеть; легаси-поле `ttl_hours` тоже принимается
  (конвертируется в минуты, `ttl_minutes` при обоих заданных выигрывает).

Оптимизация — только суммарная цена билета в ₽ (минимум по всем
предложениям); всё остальное, что хочет пользователь, — это жёсткие фильтры
(`constraints`/`global_constraints`), никогда не участвующие в ранжировании.

## Алгоритм: две фазы

Поиск двухфазный (повышает вероятность найти дешёвые связки при меньшем
сетевом объёме, чем полный перебор комбинаций):

1. **Фаза 1 — поплечевой свип.** Каждое направление ищется независимо как
   one-way по ВСЕМ датам своего окна (per-direction фильтры применяются).
   Даёт минимум цены на каждую пару (плечо, дата). Результат — промежуточный
   отчёт `reports/<дата поиска>__<маршрут>-<месяц>/legs-<маршрут>-<месяц>.md`
   (+ JSON рядом): таблица поплечевых минимумов по датам и ранкинг комбинаций
   дат по возрастанию суммы минимумов (с учётом
   `stay_days`/монотонности/`max_trip_days`). Сумма — оценка по отдельным
   билетам; реальная цена связки берётся в Фазе 2. Фаза 1 не ограничена
   `max_requests`.
2. **Фаза 2 — точечная верификация.** CLI идёт по ранкингу по возрастанию и
   для первых N комбинаций (`--verify-top N`, по умолчанию 60) делает реальный
   multi-city поиск всей связки одним запросом. Результат — финальный отчёт
   `reports/<дата поиска>__<маршрут>-<месяц>/<маршрут>-<месяц>.md` с настоящими
   ценами связок, отсортированный по итогу. `max_requests` — жёсткий потолок
   сети этой фазы.

## Запуск
```
# из корня репозитория
uv run aviasales-search --config trip.json --curl curl.txt
```

Флаги CLI:
- `--config` (обязателен) — путь к JSON-конфигу поездки (схема выше).
- `--curl` (обязателен) — путь к файлу с `Copy as cURL` (только
  авторизация — куки/заголовки; см. «Обновление cURL»).
- `--out` — куда записать итоговый Markdown-отчёт (отчёт также всегда
  печатается в stdout, независимо от `--out`); по умолчанию
  `reports/<дата поиска>__<маршрут>-<год-месяц>/<маршрут>-<год-месяц>.md`
  в текущей директории (отдельная папка на каждый прогон, чтобы повторные
  поиски того же маршрута не затирали друг друга).
- `--verify-top N` — сколько верхних комбинаций ранкинга проверить реальным
  multi-city поиском в Фазе 2 (по умолчанию `60`).
- `--top N` — сколько комбинаций дат показать в отчёте (по умолчанию все).
- `--refresh` — игнорировать кэш зондов и искать заново.
- `--max-requests M` — переопределить `search_budget.max_requests` из конфига
  (жёсткий потолок сети Фазы 2; Фаза 1 всегда делает полный свип).
- `--cache-dir` — папка кэша (по умолчанию `./cache`).
- `--render-from <results.json>` — пересобрать Markdown и CSV из готового JSON
  результатов без нового поиска (--config/--curl не нужны). Строка дельты цен («было …») при пересборке не воспроизводится — JSON её не хранит.

Отчёт — плоская Markdown-таблица: строка = одна комбинация дат вылетов, в ней
самый дешёвый билет этой комбинации; строки отсортированы по возрастанию
итоговой цены. Колонки: `#`, `Даты`, по одной колонке на каждое плечо
поездки, `Итого`, `Ссылка` (диплинк на билет — для мультигорода/open-jaw это
ссылка на страницу поиска с датами; если ссылку построить нельзя — «—»),
`Комментарий` — альтернативы той же комбинации дат: билеты с той же ценой и
до трёх более дорогих, с пометкой `+Δ ₽` и ссылками `[↗]`.

Все файлы прогона лежат в одной папке `reports/<дата поиска>__<маршрут>-<год-месяц>/`:
финальный и промежуточный Markdown прямо в ней, рядом с финальным CLI
автоматически пишет JSON со ВСЕМИ найденными билетами
(`json/<то же имя>.json`) и CSV для фильтрации в Excel/Sheets
(`csv/<то же имя>.csv`, UTF-8 с BOM); у промежуточного отчёта Фазы 1
(`legs-<то же имя>.md`) свой JSON рядом в той же `json/`. Все файлы живые:
обновляются по ходу прогона — при обрыве (бан/Ctrl+C) в них остаётся собранное
до обрыва. Если нужно переупорядочить найденное или пересобрать отчёты после
правки — используй флаг `--render-from reports/<дата>__<маршрут>/json/<имя>.json`
(работает без `--config`/`--curl`, сеть не нужна; папка вывода берётся по дате
исходного поиска из JSON, а не по дате пересборки).

Коды возврата: `0` — успех; `1` — ошибка конфига (файл не найден, битый
JSON, не прошла валидация схемы), ошибка файла `--render-from` (нет файла/битый JSON/чужая schema_version), или запуск поиска без `--config`/`--curl`; `2` — cURL протух/забанен (файл не
найден/не парсится, либо API вернул 401/403/429/5xx или маркер anti-bot
challenge в теле ответа) — нужен свежий `curl.txt`.

## Обновление cURL
cURL — это ТОЛЬКО авторизация (куки и заголовки браузера, включая
`x-aws-waf-token`); тело запроса CLI строит сам. Нужен именно запрос
**start** — WAF start-хоста отклоняет заголовки, скопированные с
results-запроса (у start есть дополнительные, например `x-web-client`;
проверено вживую 2026-07-28):
1. Открой https://www.aviasales.ru в Chrome.
2. F12 → вкладка **Network** → впиши в фильтр `start`.
3. Выполни любой простой поиск; правый клик по запросу `start` к
   `tickets-api.aviasales.ru/search/v2/start` → **Copy** → **Copy as cURL (bash)**.
4. Сохрани в файл `curl.txt` в корне репозитория (или передай ассистенту).

## Безопасность
- `curl.txt` содержит ЖИВЫЕ куки/токены сессии (включая WAF-токен) — это
  фактически ключ доступа к текущей сессии на aviasales.ru. **Никогда не
  коммитить** `curl.txt` (и `curls.txt`), а также `trip.json` и папки
  `reports/`/`cache/` (могут содержать личные данные о планах поездки). Все
  они уже перечислены в `.gitignore` — не убирай их оттуда.
- Поиск идёт с IP пользователя и его куки. У aviasales есть бот-защита
  (WAF + botScoring + невидимая smartCaptcha) — не увеличивай
  `--max-requests` без необходимости; между сетевыми вызовами уже встроены
  паузы. При HTTP 403/429 или капче в ответе CLI сам остановится с кодом 2 —
  обнови `curl.txt` и повтори запуск.

## Кэш
- `cache/probes.jsonl` — сырые зонды (одна комбинация дат
  направлений + пассажиры + класс + требование багажа → список билетов),
  переиспользуются `cache.ttl_minutes` минут.
- `cache/runs/<дата-время>/` — снапшот прогона: `trip.json`
  (конфиг как он был использован, включая override `--max-requests`),
  `offers.jsonl` (прошедшие фильтры билеты, по убыванию цены), `report.md`,
  `search.log` (лог перебора комбинаций дат, см. ниже).
  Если находится предыдущий снапшот с тем же маршрутом/пассажирами/классом/
  фильтрами, новый отчёт покажет дельту цены к нему.

## Прогресс и лог перебора
Во время прогона CLI пишет в stderr (и дублирует в
`runs/<дата-время>/search.log`) заголовок и по одной строке на каждую
комбинацию дат — процент выполнения, даты направлений, источник данных
(`сеть`/`кэш`/`пропуск` при исчерпанном сетевом бюджете), сколько билетов
найдено, сколько прошло фильтры, лучшую цену комбинации и бегущий минимум с
начала прогона (`★` — эта комбинация улучшила минимум). По бегущему минимуму
удобно решать, что цена уже устраивает, и останавливать перебор вручную —
перезапуск мгновенно соберёт отчёт из кэша:
```
Комбинаций дат: 300, сетевой бюджет: 400, кэш TTL: 60 мин
[ 12/300   4.0%] MOW→DPS 2026-09-07 | DPS→MOW 2026-11-01 | сеть | найдено 60 | прошло 8 | лучшая 145 231 ₽ | мин. с начала 145 231 ₽ ★
[ 13/300   4.3%] MOW→DPS 2026-09-07 | DPS→MOW 2026-11-04 | кэш | найдено 55 | прошло 6 | лучшая 149 810 ₽ | мин. с начала 145 231 ₽
```
За живым прогрессом фонового прогона удобно следить через
`tail -f cache/runs/<дата-время>/search.log`; stdout занят только
финальным Markdown-отчётом и не замусоривается прогрессом.

Файлы отчётов — «живые» всегда (не только при явном `--out`): они атомарно
перезаписываются по ходу прогона при каждом изменении таблицы (комбинации
дат, цены, ссылки всегда актуальны), поэтому даже при обрыве прогона (бан,
Ctrl+C) в них остаётся лучшее из уже найденного. Путь по умолчанию —
`reports/<дата поиска>__<маршрут>-<год-месяц>/<маршрут>-<год-месяц>.md` в
текущей директории (одновременно пишутся JSON в `json/` и CSV в `csv/` внутри
той же папки прогона, с тем же именем); `--out` переопределяет путь к
MD-файлу и соответственно к двум остальным.

## Тесты
`uv run pytest` — офлайн, без сети (транспорт мокается; `curl_cffi` не
требуется для тестов, используется только боевым транспортом).

## Живой прогон (ручная процедура)
1. Получи свежий `curl.txt` (см. «Обновление cURL» выше).
2. Из корня репозитория: `uv sync --extra live`.
3. `uv run aviasales-search --config trip.json --curl curl.txt`.
4. Если ответ HTTP 200, но билеты не извлеклись — единственное место
   маппинга полей ответа `/results` в билеты — `extract_tickets` в
   `aviasales_search/results_parser.py`. Сравни форму реального ответа с тем,
   что ожидает парсер (структуру `tickets[]`/`proposals[]`/`flight_legs[]` —
   читай прямо из `results_parser.py`), поправь маппинг под реальную схему,
   при необходимости обнови фикстуру `tests/fixtures/results_v32_sample.json`
   (без реальных токенов — эта фикстура содержит только данные о рейсах).
   (Локально, если файл ещё на диске: `docs/aviasales-api-v3.2.md` — точная
   схема запросов/ответа, проверенная вживую; этот файл в `.gitignore` и не
   попадает в git, так что в свежем клоне его не будет.)
