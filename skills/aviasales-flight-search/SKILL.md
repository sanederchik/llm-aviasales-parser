# Aviasales Flight Search

## Что делает
Находит лучшие (минимум суммарной цены в ₽) варианты перелётов, в т.ч. сложные
мультигород-маршруты. Пользователь описывает поездку словами — ты собираешь
`trip.json` и запускаешь CLI. CLI ходит в реальный внутренний API aviasales.ru
(двух-хостовый флоу `start` → `results`): вся поездка (все направления сразу)
ищется ОДНИМ запросом, авторизуясь куки/заголовками из cURL, скопированного
из браузера пользователя (тело запроса CLI строит сам). Результаты кэшируются
и рендерятся в три файла: Markdown-отчёт (таблица, строка = комбинация дат
вылетов, самый дешёвый билет комбинации + альтернативы в комментарии,
сортировка по итоговой цене), JSON со ВСЕМИ найденными билетами
(первоисточник, сортировка по цене) и широкую CSV-таблицу для фильтрации в
Excel/Sheets: одна строка = один билет, по каждому плечу отдельные столбцы
(дата, вылет, прилёт, длительность в минутах, авиакомпания, пересадки).

## Рабочий процесс

1. **Выбери режим настройки.** Первым же сообщением предложи пользователю
   выбор (через AskUserQuestion, если инструмент доступен; иначе обычным
   вопросом в чате):
   - **Упрощённый поиск** — блокирующе уточняются только содержательные
     параметры (см. таблицу ниже); технические берутся дефолтами, но
     обязательно показываются в брифе перед запуском.
   - **Глубокий поиск** — анкетирование по ВСЕМ параметрам, включая
     технические.

2. **Собери параметры. Молча придумывать значение содержательного параметра
   ЗАПРЕЩЕНО** — всё, что пользователь не сказал явно, спроси до запуска.
   Правила:
   - Группируй вопросы: до 4 за раз через AskUserQuestion с осмысленными
     вариантами ответов (без него — компактные нумерованные списки), а не
     десять отдельных сообщений подряд.
   - Явный ответ «не важно / без разницы» валиден: зафиксируй параметр как
     «без ограничения», покажи это в брифе и НЕ переспрашивай.
   - Из слов пользователя выводи всё, что выводится однозначно («нас двое» →
     2 взрослых — это `указано`, не выдумка); спрашивай только настоящие
     пробелы.

   | Группа | Параметры |
   |---|---|
   | Содержательные — уточнять в ОБОИХ режимах | маршрут (направления); окно дат каждого направления; `stay_days` (min/max дней) для каждой промежуточной точки; `max_trip_days`; пассажиры; класс (`trip_class`); багаж (наличие + `baggage.min_weight_kg`, ручная кладь `large_handbag`); `max_transfers`; `max_transfer_minutes`; `max_duration_minutes`; время суток вылета/прилёта или точное время `depart_time`/`arrive_time`; исключённые аэропорты пересадок / Персидский залив; конкретные `from_airports`/`to_airports`; авиакомпании; `max_price`; тариф с обменом/возвратом (`changeable_only`/`refundable_only`) |
   | Технические — уточнять только в глубоком режиме, иначе дефолты | `currency`; `market_code`; `search_budget.max_requests`; `date_samples_per_direction`; `request_delay_seconds`; `cache.ttl_minutes`; `--top` |

3. **Покажи бриф и дождись подтверждения.** Перед запуском CLI выведи полную
   расшифровку будущего `trip.json` человеческим языком — каждый параметр с
   пометкой источника: `указано` (из слов пользователя), `уточнено` (из
   ответов на твои вопросы), `дефолт` (технический параметр в упрощённом
   режиме). Затем спроси «запускаем?». БЕЗ подтверждённого брифа CLI не
   запускается — никогда.

4. **Составь `trip.json`** по схеме (см. `README.md` в корне плагина →
   «Схема конфига»).
   Ключевое:
   - `directions` — список ВСЕЙ поездки целиком (туда-обратно или мультигород
     — несколько записей в одном списке, не отдельные one-way запросы).
     Каждая запись: `from`, `to`, обязательное `date_window: {earliest,
     latest}` (Claude вычисляет окна дат из NL пользователя, например «2
     недели в Стамбуле» → окно дат вылета следующего направления), опционально
     `constraints`, переопределяющие `global_constraints` для этого
     направления.
   - `stay_days: {min, max}` у направления — пребывание в его пункте
     назначения: дата вылета СЛЕДУЮЩЕГО направления обязана попасть в
     `[дата_вылета + min, дата_вылета + max]` (границы включительно;
     считается по датам вылета, погрешность ±1 день от времени прилёта).
     «Пробуду на Бали 30–50 дней» → `stay_days: {"min": 30, "max": 50}` у
     направления, ПРИЛЕТАЮЩЕГО на Бали. На последнем направлении запрещён.
   - `global_constraints` — дефолтные жёсткие фильтры на все направления:
     `max_transfers`, `max_transfer_minutes`, `baggage: {required,
     min_weight_kg, large_handbag}` (легаси `baggage_required` тоже
     работает), `max_price`, `max_duration_minutes`,
     `depart_time_of_day`/`arrive_time_of_day` (`morning|afternoon|evening|
     night`) или точный диапазон `depart_time`/`arrive_time: {"from":
     "HH:MM", "to": "HH:MM"}`, `exclude_gulf_transfers: true` (исключить
     пересадки через Персидский залив) или явный `exclude_transfer_airports`,
     `airlines` — белый список IATA-кодов авиакомпаний (каждый рейс, включая
     стыковочные, должен выполняться перевозчиком из списка),
     `changeable_only`/`refundable_only` (только обмениваемые/возвратные
     тарифы), `alliances`/`agents`/`payment_methods`/`aircraft_models`/
     `lowcosts`/`no_night_transfers`/`no_complex_transfers`/
     `no_recheckin_transfers`/`no_interlines`/`convenient_transfers` (только
     серверная фильтрация — уходят в `filters_state` results-запроса, у
     клиента нет данных для перепроверки). Направление может задать
     `from_airports`/`to_airports` — конкретные аэропорты города вылета/
     прилёта. Полный список и семантика — в README → «Схема конфига».
   - `max_trip_days` (опционально, верхний уровень) — макс. число дней между
     датой вылета первого направления и датой вылета последнего («вся поездка
     не дольше N дней»).
   - `passengers`, `trip_class`, `currency`, `market_code`.
   - `search_budget.max_requests` (деф. 100) и `date_samples_per_direction`
     (деф. 10) — верхний предел реальных сетевых запросов и плотность сетки
     дат (кэш-хиты бесплатны); понижай при риске бот-блокировки.
   - `search_budget.request_delay_seconds: {min, max}` (деф. 0.5–1.0) —
     диапазон «человеческой» паузы в секундах перед каждым HTTP-вызовом;
     повышай при риске бот-блокировки, понижай ради скорости.

5. **Убедись, что есть свежий `curl.txt`.** Если его нет или CLI ранее вернул
   код 2 (протух/забанен) — дай пользователю инструкцию из раздела
   «Обновление cURL» ниже и дождись файла.

6. **Проверь окружение и запусти CLI.** Python-проект (файл `pyproject.toml`
   со скриптом `aviasales-search` и пакет `aviasales_search`) лежит в корне
   репозитория, т.е. на два уровня выше папки этого скилла.

   **6a. Определи корень проекта (`ROOT`):**
   - Плагин Claude Code: `ROOT=${CLAUDE_PLUGIN_ROOT}` — Claude Code при
     загрузке скилла уже подставил сюда реальный путь установленного плагина;
     если в строке выше стоит конкретный путь, просто используй его.
   - Codex или другой раннер (строка выше НЕ подставилась — в ней осталось
     имя переменной CLAUDE_PLUGIN_ROOT в фигурных скобках): возьми папку
     этого SKILL.md, разреши симлинк и поднимись на два уровня:
     ```bash
     ROOT="$(dirname "$(dirname "$(dirname "$(readlink -f <путь к этому SKILL.md>)")")")"
     ```
     (скилл лежит в `<repo>/skills/aviasales-flight-search/`, значит `ROOT` —
     корень репозитория). Проверка: в `$ROOT` есть `pyproject.toml` со
     скриптом `aviasales-search`.

   **6b. Проверь `uv` (единственная внешняя зависимость):** выполни
   `uv --version`. Если `uv` нет — скажи пользователю и установи официальным
   инсталлятором:
   ```bash
   curl -LsSf https://astral.sh/uv/install.sh | sh   # macOS/Linux
   ```
   (Windows: `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`;
   после установки бинарь может лежать в `~/.local/bin` — добавь его в `PATH`
   текущей сессии). Отдельно ставить Python не нужно: `uv run` сам скачает
   Python 3.14 и зависимости проекта при первом запуске.

   **6c. Запусти поиск.** Рабочие файлы (`trip.json`, `curl.txt`; отчёты и
   кэш CLI сам сложит в `reports/` и `cache/`) держи в текущей рабочей
   директории пользователя, проект укажи флагом `--project`, живой транспорт
   требует extra `live` (ставит `curl_cffi`):
   ```
   uv run --project "$ROOT" --extra live aviasales-search --config trip.json --curl curl.txt
   ```
   Отчёт сам ляжет в `reports/<маршрут>-<год-месяц>.md` (живой файл,
   обновляется по ходу прогона), кэш и логи — в `cache/` текущей директории;
   `--out` нужен только чтобы переопределить путь. Полезные флаги: `--top N`
   (сколько комбинаций дат показать, по умолчанию все), `--refresh` (искать
   заново, игнорируя кэш), `--max-requests M` (шире перебор дат).

   Рядом с MD-отчётом CLI кладёт JSON-первоисточник
   (`reports/json/<то же имя>.json`, все билеты с полными данными плеч) и
   CSV для фильтрации (`reports/csv/<то же имя>.csv`, UTF-8 с BOM — открывается
   в Excel без кракозябр). Все три файла живые: обновляются по ходу прогона.
   Если пользователь просит отфильтровать/переупорядочить найденное или
   пересобрать отчёты после правки рендеров — сети не нужно:
   ```
   uv run --project "$ROOT" aviasales-search --render-from reports/json/<имя>.json
   ```
   (работает без `--config`/`--curl` и без extra `live`; `--out`/`--top`
   применимы). Строка дельты цен («было …») при пересборке не воспроизводится — JSON её не хранит.
   Для ответов на вопросы вида «покажи только прямые DPS→MOW
   дешевле N» читай CSV/JSON сам — не гоняй новый поиск.

   **6d. Показывай прогресс пользователю ЯВНО, прямо в чате.** CLI пишет
   прогресс в stderr и дублирует в `cache/runs/<дата-время>/search.log`:
   заголовок (`Комбинаций дат: N, сетевой бюджет: M…`) и по
   строке на комбинацию с процентом, датами, источником (`сеть`/`кэш`/
   `пропуск`), счётчиками билетов, лучшей ценой комбинации и бегущим
   минимумом с начала прогона (`★` — минимум улучшился). Длинный прогон
   запускай в фоне, но НЕ отправляй пользователя смотреть лог самостоятельно
   (`tail -f` — только как опция для желающих): по умолчанию раз в минуту
   (если пользователь попросит другой темп — используй его), а также
   при каждом улучшении минимума `★`, сам читай хвост лога и публикуй
   пользователю в чат короткую сводку — процент выполнения, сколько
   комбинаций пройдено, текущий бегущий минимум и его даты. Бегущий
   минимум важен: пользователь может решить, что цена уже устраивает, и
   попросить остановить перебор — тогда останови процесс и собери отчёт
   перезапуском (кэш отдаст всё найденное мгновенно, сеть не понадобится).

7. **Обработай результат:**
   - Код 0 → покажи пользователю отчёт из `reports/<маршрут>-<год-месяц>.md`
     (тот же путь, что CLI выбрал автоматически; самый свежий отчёт:
     `ls -t reports/ | head -1`).
     Если пользователю нужна фильтрация по параметрам плеч (авиакомпания,
     длительность, время вылета) — используй `reports/csv/<имя>.csv` (все
     билеты, не только лучшие) или JSON рядом.
   - Код 2 → cURL протух или сработала защита от ботов: попроси обновить
     (раздел ниже), затем повтори запуск.
   - Код 1 → ошибка конфига: почини `trip.json` по сообщению об ошибке и
     повтори.

8. **Кэш.** По умолчанию зонды переиспользуются `cache.ttl_minutes` минут (по
   умолчанию 5; легаси `ttl_hours` тоже принимается) — сеть не дёргается
   лишний раз. Если пользователь просит
   «поищи заново» — добавь `--refresh`. Снапшоты прогонов лежат в
   `<cwd>/cache/runs/<дата-время>/`; при повторном прогоне того же
   маршрута отчёт покажет дельту к прошлой лучшей цене.

## Обновление cURL (объясни пользователю по шагам)

cURL — это ТОЛЬКО авторизация: куки и заголовки браузера, включая
`x-aws-waf-token`. Тело запроса CLI конструирует сам из `trip.json`. Нужен
именно запрос **start** (живая проверка 2026-07-28: WAF start-хоста режет
запросы с заголовками, скопированными с results-запроса, — у start есть
дополнительные заголовки, например `x-web-client`):
1. Открой https://www.aviasales.ru в Chrome.
2. Нажми F12 → вкладка **Network** → впиши в фильтр `start`.
3. Выполни любой простой поиск (например, Москва → Санкт-Петербург), чтобы
   в списке появился запрос `start` к `tickets-api.aviasales.ru/search/v2/start`.
4. Правый клик по нему → **Copy** → **Copy as cURL (bash)**.
5. Вставь ассистенту или сохрани в файл `curl.txt` в текущей рабочей
   директории.

## Важные замечания
- Поиск идёт с IP пользователя и его куки. У aviasales есть бот-защита
  (WAF + botScoring + невидимая smartCaptcha) — держи объём запросов
  небольшим, не увеличивай `--max-requests` без необходимости; между
  сетевыми вызовами уже встроены человекоподобные паузы. При HTTP 403/429
  или капче в ответе CLI сам остановится с кодом 2 — в этом случае нужен
  свежий `curl.txt` (см. выше), а не повтор с теми же куками.
- **Безопасность/секреты:** `curl.txt` содержит живые куки/токены сессии
  пользователя (ключ доступа к его сессии на aviasales.ru). Никогда не
  предлагай закоммитить `curl.txt`/`curls.txt`, а также `trip.json`, папки
  `reports/` (личные данные о планах поездки) и `cache/` — все они в
  `.gitignore`.
- Если Aviasales поменяет схему ответа `/results`, править нужно только
  `extract_tickets` в `aviasales_search/results_parser.py` (см. README →
  «Живой прогон»).
